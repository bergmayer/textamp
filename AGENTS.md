# Textamp Project Instructions

## Build and verification

During implementation, run focused tests for the affected behavior and use the
development build for interaction checks. Reuse the same target directory,
toolchain and profile settings throughout the task. Do not run the full suite or
optimized release builds after each intermediate edit.

Routine changes require focused checks for behavior plausibly affected by the edit,
plus formatting and compilation of the affected frontend. Use targeted integration
tests for shared playback/source logic and deterministic desktop interaction tests
for changed controls or layouts. Run scoped Clippy when Rust changes warrant it;
prefer `--lib` for application code rather than building every test target.
Do not run full suites, both frontend graphs, release builds, or repeated checks
merely as a delivery ritual. Reserve broad validation for releases, broad refactors,
failures suggesting wider impact, or an explicit request. A relevant interaction
check is more useful than unrelated protocol tests. Repeat checks only when a
subsequent edit could change their result or a failure remains unresolved.

For focused desktop tests, use `cargo test --features desktop-tests --lib <filter>`
to avoid compiling and launching every integration-test target. Use
`packaging/macos-desktop/build.sh --preview` for routine GUI iteration and review;
it reuses the development/test feature graph and the existing Preview bundle.
Do not perform optimized builds for routine previews. Build optimized artifacts
when explicitly requested for release, distribution, installation of a release
build, or optimization/performance verification. Release verification uses
`cargo build --release --bin textamp` and, for desktop delivery,
`cargo build --release --features desktop --bin textamp`.

For documentation or build-workflow-only changes, validate the edited documents,
configuration and scripts directly; a full application rebuild/test cycle is not
required unless the change affects application behavior or release output.

Run Cargo commands sequentially. Check for an existing Cargo job in this checkout
before starting another; do not compete for its build directory or delete its
artifacts. Do not stop another task's build without authorization.

Use isolated XDG configuration/data/cache/state directories for automated app
tests. The Unix Cargo runner isolates test executables automatically; preserve this boundary.
Direct executable/native interaction checks must also set all four XDG paths. Live tests that change playlists, favorites, ratings or play history must
use the dedicated loopback fixture, never a personal music server. Audio tests
use `DummyBackend` or explicitly opt into native hardware.

The optional development desktop target is `cargo build --features desktop-tests --bin textamp`.
Keep the default TUI build and behavior intact when changing shared code.

## Build artifact hygiene

Cleanup is routine work for this project, not an optional follow-up or something
that requires another user reminder. Before finishing build/test work, inspect
project disk usage and remove superseded builds and large disposable files
generated by the task. Identify ownership before deleting large or unfamiliar
files; preserve user data and unrelated work.

Keep one reusable development/test cache in `target/debug` and one current
release cache in `target/release`. A completed verification run does not make
either cache obsolete. Do not routinely delete `target/debug` or run `cargo clean`.
Do not accumulate separate target directories or copies of test app bundles.
Development/test profiles disable debug symbols by default; keep their normal
incremental compilation enabled. Keep the codec and FFT package optimizations in
Cargo.toml: previews must decode and analyze audio at interactive speeds without
whole-application release optimization. Avoid per-command profile overrides that create
different artifact variants. Override debug symbols only when needed for a
debugger, and remove those disposable variants afterward.

Budget 20 GiB for the combined development/test and release caches. Measure before
and after build work. Below that budget, retain compiled dependencies and useful
incremental state. If the budget is exceeded and no builds are running, remove
identified obsolete feature/profile variants and superseded executables first;
then discard incremental state if needed. A full cache purge is a last resort for
a corrupt cache or disk pressure, not an end-of-task step. If current required
artifacts alone exceed the budget, report their size rather than repeatedly
deleting and rebuilding them.

After verification, stop owned temporary apps and fixture servers and remove
disposable test bundles and isolated fixture profiles. Preserve the current
deliverable, installed app/launcher, credentials, music and unrelated files.

## Frontend feature parity

New music-library, discovery, queue, playback, caching and other domain features
must be available in both the TUI and desktop frontend wherever the operation
makes sense. Keep their reducers, source routing, request identity and task
ownership shared. Expose the capability through each frontend's appropriate
controls; preserve the TUI's independent key bindings and complete behavior.
Artist-name navigation must work from visible metadata and result labels in both
frontends when the artist has a catalog destination. Keep the shared core suitable
for a future mobile frontend: music policy, validation, source routing, caching,
request identity, cancellation and navigation intent belong in shared actions,
reducers or services. Frontends may project that state and translate gestures into
shared commands, but must not implement competing domain rules. Core modules must
not depend on GPUI, Ratatui or native windowing APIs. Test domain changes without
enabling desktop features as well as through the affected frontend. Pure windowing, animation,
layout and platform controls may remain frontend-specific. Verify interaction
behavior in both frontends and document any concrete capability limitation.

## Desktop component policy

This policy applies only to the GPUI GUI. It does not require GPUI or GPUI Kit
in the TUI, and does not authorize replacing or redesigning the terminal frontend.
For TUI changes, prefer existing Ratatui widgets or established compatible widget
crates when they meet the interaction requirements; keep necessary music-specific
rendering and preserve the terminal frontend independently.

The GPUI desktop frontend MUST use off-the-shelf **GPUI Kit** components wherever
an available component can meet the requirement. This is a blanket project rule,
not limited to individual refactors. Inspect the pinned Kit APIs before building
a custom widget. Use Kit forms/fields, inputs, buttons, lists/list items, tabs,
menus, dialogs, breadcrumbs, description lists, empty states, status bars and
scrollbars rather than manually reproducing them. Every scrollable desktop pane
must expose an appropriate Kit scrollbar. Preserve stock components already used.

Custom rendering/composition is appropriate for music-specific content, audio
visualizers, Miller-column arrangement and app/native-platform behavior that Kit
does not supply. If a Kit component cannot satisfy required interaction semantics,
record the concrete limitation and retain only the necessary custom behavior.
Do not add wrappers that merely rename components. Delete custom implementations
when a Kit replacement supersedes them. This policy must not remove or degrade
the complete TUI frontend.

Global desktop command-palette actions must also be available in the native menu
bar. Reuse the shared command definitions and keep the menu coverage regression
passing. Selection-specific track operations belong in context menus and the
palette; provider capabilities and source identity still govern execution.

## macOS design policy

The desktop GUI targets the appearance and behavior of a standard SwiftUI macOS
app. Current Apple Human Interface Guidelines are the default for every primary
and secondary window: control semantics, native window behavior, navigation,
menus, keyboard focus, typography, spacing, colors and accessibility. This policy
does not alter the TUI's independent presentation or shortcuts.

Use GPUI Kit components when they meet the requirement, with consistent macOS
styling and sizing. Kit's cross-platform defaults are not themselves evidence of
Mac HIG conformance. Inspect the pinned APIs before adding custom UI. Use native
platform services for system-owned interactions such as file/folder selection
and alerts when Kit cannot meet their native behavior. Keep native window chrome;
do not paint replacement traffic lights or imitate Liquid Glass with gradients.

Choose controls by meaning: checkboxes for independent booleans; radio groups or
pop-up pickers for mutually exclusive settings; pull-down menus for commands;
steppers/number inputs for bounded counts; masked inputs for credentials. Declare
default, cancel and destructive actions explicitly; never infer them from button
position or wording. Keep normal Settings changes immediate, with explicit
Save/Cancel only for staged connection or document edits.

Use the system UI font, semantic Mac text roles and colors, and consistent layout
tokens. Respect appearance, accent, contrast, transparency, motion and keyboard
accessibility settings. Verify active and inactive windows, focus indication,
readable labels, selection, and resize behavior. Specify native-control geometry
against the supported macOS versions rather than applying iOS touch dimensions
or arbitrary per-window sizes.

Record every intentional departure and its concrete reason in
[docs/DESKTOP.md](docs/DESKTOP.md). A renderer limitation can justify a particular
fallback, not an unrelated redesign or silent loss of functionality. Distinguish
source inspection, automated behavior checks and native visual verification;
never claim HIG conformance solely from compilation or component usage.

## UI consistency

Update relevant shortcut bars in `src/ui/app.rs`, the shared help text in
`src/util/help_text.rs` (rendered by `src/ui/screens/help.rs`), layout comments,
and README when functionality changes.

Clicking to highlight must not recenter the viewport. Set the `scroll_pin` on
click and clear it on keyboard navigation. Settings/library management must
support both mouse and arrows; opening it must not switch libraries or play.

## Architecture

Textamp retains its complete terminal frontend and has an optional GPUI desktop frontend. Supported sources are Subsonic/Navidrome,
local folders and WebDAV, with optional AudioMuse analysis.

```text
UI: src/ui (pure render-from-state)
  ↓ input actions / render feedback
App: src/app (state, reducers, task ownership, event loop adapters)
  ├─ src/app/sources (provider routing and orchestration)
  │    ├─ src/navidrome (OpenSubsonic HTTP and normalized catalog)
  │    ├─ src/audiomuse (analysis/discovery HTTP)
  │    └─ src/library (shared models, local/WebDAV, persistent caches)
  ├─ src/services (UI-independent business logic)
  ├─ src/media (artwork, waveform and spectrogram caches/analysis)
  └─ src/audio (local decoding/output; no UI or library API imports)
```

`AppState` is the source of truth; events carry user input or asynchronous
completions, actions change state, and UI rendering consumes state. UI does not
own state or effects. App-core modules must not import `src/ui`.

Provider capabilities determine available operations. Shared queue, radio and
playback reducers must not issue provider-specific HTTP requests. Use the source
boundary, retaining library and operation identity on successes and failures.
Task leases cancel superseded work. Never convert an error into a successful
empty catalog or overwrite a newer selection with an older response.

Avoid adding wrappers or traits without a concrete benefit. Reuse shared models
and preserve their serialized compatibility with existing non-Plex caches.

## Libraries, views and caches

F3 switches libraries; F2 → Libraries manages sources/accounts. Startup opens the
saved selection, then another saved source if needed; no source opens normal
browsing with an add-library prompt. Startup must not start playback.

Settings uses a flat category list (Libraries, Appearance, Audio,
Sidebar, Search, About) and one content pane. Up/Down selects categories;
Enter/Right enters controls; Tab/Shift+Tab switches panes; Left/Esc returns to
categories, Esc there closes. F10 focuses categories. Narrow terminals show
one pane at a time. The command palette works in settings.
Setup and its dialogs use the active app theme.
Libraries is grouped by provider/account. Up from its first row focuses the
category list. Enter opens General / Analysis / Cache pages; Left/Right changes
pages. The library detail card stays concise. Add opens a type chooser and a single form.
Saving a connection must not activate a different library. Child forms return to
the owning setup page. F3 remains switch-only. Cache jobs must not switch the
active source or playback. Artwork downloads and their clear action are scoped
to individual libraries, alongside metadata and analysis caches.
Artwork rendering and default album-column visibility are per library; restore
both on source switches and show the active library in Artwork settings. Legacy
global values are fallback defaults. The downloaded image cache is per library.
Sidebar visibility belongs in Textamp settings. Theme artwork uses the active
theme unless a different theme row has content focus. Cache sizes are measured
on disk per library (including AudioMuse), not estimated from in-memory structs.

Browse uses Miller columns. Ctrl+L opens Library, Ctrl+G genres, Ctrl+O folders,
Ctrl+F search, Ctrl+U queue, Ctrl+N Now Playing, F1 help. Tab switches Library /
Now Playing focus, including split mode. `:` is the command palette; `:q` quits.
Keep the help text authoritative for all other bindings.
Describe music uses Enter for its prompt and arrow keys for browsing history/results.
Keep successful description history scoped to the exact library; results use the
playlist-style two-row layout. Search and Similar Tracks open adjacent details on
Enter, with explicit Play Track / Play Track++ actions. Queue Enter still plays.
Playback uses the system audio output; there is no in-app output selector.

All sources have persistent metadata caches: server catalogs, directory trees and
visited album listings. Cached startup comes first, weekly refresh plus manual F5.
AudioMuse shares that policy. Local/WebDAV tree scans are bounded and keep only
directory structure; leaf track listings remain lazy. Never download audio as
part of a cache scan or replace a complete tree with a partial failed scan. Failed refreshes preserve the last usable cache. These are metadata
caches, not offline music downloads.

Honor XDG overrides before platform defaults. macOS configuration, credentials and
logs default to `~/Library/Application Support/textamp`; caches to
`~/Library/Caches/textamp`. Credentials are separate private files. Do not print
secrets, alter personal credentials during tests, or delete music when removing
an account/library.

## Installation

When asked to update the installed macOS build, verify and replace
`~/Applications/Textamp.app` with the self-contained desktop-enabled `textamp`
bundle. Preserve the standalone cross-platform TUI build. The installed bundle
supports `--gui`, `--text` and `--terminal`; do not install a second independent
GUI or external-terminal launcher. Remove verified superseded installations only
after the replacement works. Do not commit or publish without instruction.

On a personal iPhone or iPad, update Textamp in place. Before installing, make
a private device-specific backup of the saved library configuration and its
credential files. Read those files back after installation and verify that the
library records survived. Keep the backup until verification succeeds. Never
uninstall Textamp or use container replacement to install a build or clean up
test data. Run automated fixture tests in the simulator or under a separate
test app bundle identifier on hardware.
